# 门禁上行语音本地验证（2026-11-15）

## 范围

用户当前不方便现场呼叫，暂无已确认可用的华为企业管理授权或有线 DHCP 管理途径。本轮继续完成可独立执行的排查，保持人脸感知和无人待机的原验收前提。

系统地址持久化限制与现场场景清单见[专用终端验收记录](dedicated-intercom-acceptance.md)。

代码基线为 `e3fb563`。本轮仅在独立 API 31 / API 36 模拟器验证，不修改平板、网口、铃声音量或运行参数，不发起真实呼叫、开锁或呼梯。模拟器以 `-no-audio` 启动；采集内容不保存为录音文件。

## 已确认并修复的并发问题

`AppConnection.retryCallAudio()` 的工作线程通过检查后，会将音频启动回调排入主线程。用户挂断会先立即停止声音并设置 `callEnding=true`，工作线程稍后才完成协议挂断。原回调只核对来电键和 `ANSWERED`，因此在这个间隙仍可能重新启动音频。

先用工作线程屏障固定上述顺序，原代码实际失败于 `Queued retry restarted microphone capture while the call was ending`，耗时 3.544 秒。修复仅为主线程回调增加 `!currentState.callEnding`，与既有来电声音启动条件一致，没有增加新的资源所有者或状态。

第一轮复审另指出测试的 400 毫秒等待可能受调度延迟影响；已改为在工作线程仍阻塞时排空主线程队列，再检查没有新的采集状态。该问题已得到本地复现，但尚无证据将其认定为现场持续上行无声的原因。

## 上行链路集成检查

新增 `CallAudioUplinkTest`，所有用例仅允许在 `ranchu` 模拟器运行。两项采集用例使用真实 `AudioRecord`、`CallAudio`、`AppConnection` 和 `IncomingCallSession`，仅将最后的门机传输替换为现有假传输：

- 接听前无上行，允许采集后至少三个 PCM 块到达传输层；报文可解码，包含 512 字节 PCM、正确的本户/门机身份和递增序号；挂断后不再继续发送。
- 先接听但不启用采集，再重试声音，能够产生上行报文；接听控制请求仍只有一次。
- 挂断期间已排队的音频重试不能重新开始采集。

这些用例覆盖采集回调到控制器、会话编码与传输交接的连接点。模拟器 PCM 可以是全零，测试不把包存在解释为声音可听，也未覆盖来电页授权交互、接待服务的麦克风前台类型升级、实际平板录音路由或门机接收/播放。

## 剩余验收

现有调试统计中，`CAPTURE=AVAILABLE` 表示录音启动返回；`sent=0` 仍不能单独区分未读到完整 PCM 与发送前校验拒绝。`sent>0` 且 `non_silent>0` 可以证明非零 PCM 已交给传输并成功返回，不能证明门机已收到或播放。

下一次具备现场条件时，结合当前通话的健康状态、收发统计和双方实际听音继续区分硬件采集、传输与门机播放；当前不猜改采样率、音频源或回声处理参数。IP 持久化的系统权限阻断、真实双向声音、完整前后台/锁屏来电和 24/72 小时观察仍保留未通过状态，不进入感知待机。
