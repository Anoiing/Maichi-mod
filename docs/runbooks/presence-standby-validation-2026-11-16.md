# 人脸感知与应用内低亮待机验证（2026-11-16）

## 范围与版本

本轮从干净的 `b11cc8c` 开始，没有上一轮待审查或待提交的代码。用户明确要求按刚更新的专用终端方案和计划继续开发任务 7，因此提前完成本地开发；这项执行顺序调整不表示任务 6 的现场条件或 24/72 小时观察已经通过。

目标是应用内低亮待机和本地人脸感知。系统真正息屏后的摄像头唤醒未开放，也没有新增相机前台服务、后台相机、全局亮度修改、自动开锁或人脸身份识别。

## 实现与支持范围

- 「设置 → 终端与接待 → 感知与待机」有“无人低亮待机”和“人脸感知亮屏”两个开关，首次均关闭。低亮开启后可选用人脸感知；拒绝相机权限仍可使用触摸待机。
- 正常亮度跟随系统；30 秒无操作且没有确认有人时，当前门禁窗口降至 5%，并暂停既有首页光束/流星刷新。触摸、按键以及设置弹窗内的点按、键入都会恢复亮度并重新计时。
- 确认有人要求至少两个连续正结果，相隔至少 800 毫秒；单帧、未知结果、超过连续性窗口的旧结果都不能唤亮。正常分析间隔至少 200 毫秒；低亮、夜间 22:00～06:00 或外部供电断开时至少 2 秒。低频下的实际确认会等待下一次采样，不能把 800 毫秒当成整个接近到亮屏的固定时延。
- 响铃、通话和监控窗口保持系统正常亮度；人脸结果不触发任何门禁命令。离开门禁到米家/其他应用、失去窗口可见性、锁屏或系统息屏时停止相机并释放本窗口的亮度/常亮请求，原接待服务继续独立运行。返回后重新给完整空闲时长。
- 电量不高于 10% 时暂停感知，同时允许系统按自身超时息屏；来电/监控仍优先常亮。断电提示不改变铃声或门禁启用意图。
- `ScreenPolicy` 是可独立运行的纯规则；`PresenceDetector` 只拥有相机和检测会话。配置独立保存在用户解锁后的 `standby.json`，不修改接待身份、闲置返回、外观配置或启动恢复逻辑。
- 固定 CameraX `1.6.2` 与 bundled ML Kit `16.1.7`。仅做前置相机分析，没有预览、相片保存或帧上传；Release 内核对存在 `assets/models_bundled/`，无需动态下载人脸模型。
- 同一检测会话一次只推理一帧，仅有一处采样间隔控制。暂停/重试会使旧回调失效；异步推理前复制像素并释放 CameraX 图像，避免旧推理占住相机。每次重新运行使用新模型客户端。
- 连续三次检测错误，或启动/运行后 10 秒没有检测结果，会停止并显示触摸回退与“重试感知”；等待资源变化或显式重试，不自动快速重绑。旧任务完成不能释放新任务的占用标记。

独立审查发现启动无结果时没有截止时间、旧推理可能阻塞新会话两个问题；分别新增 `stalledCameraTimesOutOnceAndLateFramesCannotResurrectIt` 和 `pendingOldInferenceCannotBlockRestartOrClearTheNewSessionsBusyFlag`。原实现均实际失败，修复后重跑。低频采样另用连续两次 2 秒采样确认规则测试说明实际行为。

初次使用的共享 API 36 模拟器只有后置相机，不能据此验证前置检测；本轮改建了独立的 API 31/36 前置相机模拟器。早期弹窗焦点和来电页绑定尚未完成便断言造成的测试失败，已改为等待实际窗口焦点/来电渲染状态，不修改来电业务以迁就测试。

完整测试后另在 API 31 实际操作设置开关并检查截图，两个开关、说明与原设置分组均无截断。未注入测试时钟或手工刷新策略，真实空闲 55.12 秒后的主窗口属性为 `sbrt=0.05`；点按后该属性立即清除并跟随系统亮度。这个检查证明实际计时接入生效，精确 29999/30000 毫秒边界由纯规则测试验证。截图及窗口证据仅存本机临时目录，测试设备收尾恢复两个开关关闭。

工程仍使用原生 Activity/View/XML 和原有九主题。ML Kit 间接带入 AppCompat 后对既有原生控件产生的 `AppCompatCustomView` 误报，仅在 `app/lint.xml` 中限定忽略原有两个控件文件；没有全局关闭 Lint 或更换控件体系。

## 现场边界

本轮未安装物理平板，也未改变其接待、网络或系统配置。平板同时有另一应用的安装操作，不在本轮抢占其页面。暗光、遮挡、侧脸、真实相机占用、接近到亮屏时延、长时摄像头稳定性和功耗仍待目标 MatePad 单独验证。

既有系统门禁 IP 持久化、网口重插/有线启动恢复、完整真实来电矩阵、双向声音、物理门锁/到梯及 24/72 小时观察保持未通过状态。模拟器的相机与报文结果不代替这些现场证据。
