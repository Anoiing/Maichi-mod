# 专用门禁终端交互与可靠性方案

日期：2026-11-13。状态：方案草案，供开发前评审；本文不代表新增能力已经实现或经过真机验收。

## 1. 目标和范围

平板长期专用于本户门禁。第一期交付后台来电、锁屏唤醒、断网恢复、启动恢复和必要的诊断交互；第一期通过真机验收后，再开发人脸感知亮屏与无人待机。现有原生 Kotlin、Android View/XML 界面和抓包验证过的门禁协议继续使用。

用户已确认专用用途和上述优先顺序。普通应用专用模式是本方案的建议部署方式；锁屏密码当前未知，设计和验收同时覆盖有安全锁与无安全锁两种状态。设备设置变更、安装和现场操作在后续执行阶段安排，本次只编写方案和计划。

首期来电接待范围是已有抓包依据的单元门；地库 1、地库 2 继续提供主动监控，不将单元门来电格式未经验证推广到其他门机。不增加住户身份识别、自动开锁、远程控制、云推送或访客图片/录音存档。

## 2. 当前基础与部署前提

| 项目 | 当前依据 | 本次改造要求 |
| --- | --- | --- |
| 页面生命周期 | `MainActivity.onStop()` 停止连接、铃声和语音，并结束来电 | 页面离开与停止门禁接待分开 |
| 会话 | 已有 `TerminalSession`、`IncomingCallSession`、本户/对端校验、会话代次和取消逻辑 | 保留并提升到常驻运行模块统一持有 |
| 重连 | 网络变化可重建连接；连续端口重开失败后停止自动恢复 | 有条件地持续恢复，错误配置等待修正 |
| 音视频 | 同一会话工作线程解码 JPEG；主动监控合并最新画面，来电逐帧投递 | 先统一最新帧交付并测量控制响应；不足时才分离解码并使用有界队列 |
| 平板 | 现有记录为 MatePad 11 DBY-W09、API 31；工程 minSdk 26、targetSdk/compileSdk 36 | API 31 真机与 API 36 模拟器分别验收 |
| 网口与供电 | 记录中的地址配置是临时方案，拔插/重启地址恢复和持续供电尚未完成验收 | 作为第一期现场前置检查，不能仅靠 App 参数保存判为完成 |
| 实体门禁结果 | 监控及一次呼梯有现场依据；最新来电、双向对讲及物理开锁仍待现场验收 | 区分协议回放、界面测试与实际设备结果 |

普通 App 保存本户参数、读取和核对系统网口；持久静态地址需要设备系统支持的配置方式。系统不能提供稳定地址时显示明确原因，不能通过无限重连掩盖，也不能把依赖每次电脑调试的配置算作无人值守完成。原室内机与平板的身份冲突、网口同时供电、重启恢复均应现场记录。

## 3. 部署方式比较

| 方式 | 能力与代价 | 本方案选择 |
| --- | --- | --- |
| 普通应用专用模式 | 前台服务接待、系统来电通知、锁屏来电页；配置启动和电池管理；保留系统维护入口 | 建议先采用，直接适配现有平板 |
| 受管单应用模式 | 增加锁定应用、专用桌面等设备管理能力；标准部署涉及设备重新配置，MatePad 支持情况需核实 | 后续增强，不作为第一期前提，不在本次执行恢复出厂 |
| 仅保持首页常亮 | 页面可以保持可见，但没有解决真正后台、系统锁屏和重启恢复 | 无法满足第一期目标 |

来电接待使用本地以太网，不依赖互联网、Google 推送或其他联网应用。普通模式下，系统强行停止应用后需用户重新打开；系统尚未恢复进程期间的来电无法补接，应用也不能推断当时是否有人呼叫。

## 4. 从整个项目重划职责

本项目已有可用的协议、两种传输、独立会话和取消机制。改造首先移动和收拢现有逻辑，新增能力沿现有结构接入。不会在 `AppConnection` 外再包一层 Runtime、通用命令总线或一组只负责转发的管理器。

| 现有位置 | 重构后的唯一所有者 | 具体迁移与删除 |
| --- | --- | --- |
| `AppConnection` 的线程、连接、会话、回调和代次 | 在原文件基础上重命名为 `IntercomController`，作为唯一门禁协调入口 | 重连、当前来电校验继续在这里收口；不并存两个控制器 |
| `MainActivity` 的连接创建/释放、铃声和语音启动 | 控制器持有连接与声音；新增 `IntercomService` 只承载生命周期、通知和系统保活 | 删除 Activity 中对应业务与资源管理代码，Service 不再另存一套来电状态 |
| `MainActivity` 的来电页渲染、按钮与权限交互 | 新增 `IncomingCallActivity`，复用现有 `page_call.xml` | 将现有方法整体移出主页面，移除旧来电页面分支；同一通只使用一个来电界面 |
| `ConnectionOptions` 的参数与 Activity 私有偏好读写 | 保留参数模型/校验；新增 `AppSettings` 统一持久化和启动读取 | 删除旧的页面私有存储调用，迁移后使用一份权威运行配置，不持续双写 |
| 当前网络状态图标、设置页和系统日志 | 复用 `ConnectionSettingsView` 展示接待状态、最近故障及恢复入口 | 不新建诊断应用、日志数据库、导出框架或通用状态展示系统 |
| `CallAudio` 的录音/播放 | 继续复用 `CallAudio`，把铃声收进同一声音模块，分开报告录音/播放失败 | 移除页面持有的声音资源；不另造音频策略层 |
| 重启事件 | 新增薄的 `StartupReceiver`，读取启用意图并进入同一个 Service 启动入口 | 不在接收器复制连接流程，不另造启动状态机 |

第一期预计新增四个生产 Kotlin 文件：`IntercomService.kt`、`IncomingCallActivity.kt`、`AppSettings.kt`、`StartupReceiver.kt`。`IntercomController.kt` 是现有 `AppConnection.kt` 的重构和替换；状态类型先与控制器放在一起，只有形成真实独立职责时才拆文件。继续保留现有 `TerminalSession`、`IncomingCallSession`、`DatagramTransport` 和 `JpegAssembler`，不为增加后台能力改写已经验证的协议。

状态分为连接、当前来电、音视频健康和必要系统能力，组合为控制器发布的一份 `IntercomState`。优先复用 `LinkStatus`、`TerminalState` 和 `CallStatus`；页面和通知订阅同一状态，不再分别保存可变业务副本。错误的严重程度和恢复动作通过直接映射实现，不建立可配置规则引擎。

控制处理与解码目前共用工作线程。第一期先复用现有重组/解码，统一最新帧交付并测量控制响应；只有实测达不到交互目标时，才把解码移到一个有界工作队列。届时直接调整现有接口和测试，不保留同步/异步两套长期兼容路径。

第二期仅新增 `PresenceDetector` 和可单独测试的 `ScreenPolicy`：前者处理实际相机/检测，后者决定屏幕需求。它们不能拥有门禁连接或触发开锁。每个新增模块都必须能说明它集中管理的状态，以及替代或删除了哪些原有逻辑。

每次运行使用随机运行标识，继续使用现有连接/来电代次；对页面暴露的 `CallKey` 由运行标识和来电代次组成。直接在现有操作入口验证，不增加通用命令对象、操作历史表或跨断线命令队列。进程重建、断线或来电结束立即使旧操作失效；重新打开页面只订阅快照，不重新发起接听或网络连接。

相对时间使用包含深度睡眠的单调时间计算。屏幕恢复、重新绑定页面和网络恢复时先检查截止时间；不能依靠暂停期间没有运行的界面倒计时延长旧会话。

## 5. 通用交互规则

1. 持续故障使用页面内状态或提示条，不能只弹一条很快消失的 Toast。提示写明受影响能力和一个主要恢复动作。
2. 主提示优先级是当前来电操作/结束原因、全局接待不可用、接待受限、局部功能异常、普通状态。其余问题在现有设置页的接待详情中说明，故障弹窗不能盖住接听与挂断。
3. 主动监控、呼梯、接听和开锁不可用时显示原因；设置、连接详情和返回仍可操作。禁用主按钮时，在邻近说明中保留可点击的配置/恢复入口。
4. 麦克风、扬声器、画面、人脸检测独立降级。某一能力失败不自动判定整个门禁网络断开，不停止仍可工作的能力。
5. 自动重试只用于恢复接待和网络资源。用户命令不自动重试、不跨断线排队。旧命令不能因恢复连接而补发。
6. 开锁的“已发送”是本地发送结果，不是物理开门确认；呼梯的“门机已回应”不是电梯已到达。
7. 故障恢复后更新同一状态区域；已恢复的原因仅保留为最近故障，不能继续阻断当前操作。不要求重启整个 App，不连续弹通知。不确定原因显示事实，例如“未收到门机回应”，不自行断言门机损坏。
8. 录音仅在用户接听且当前权限、音频条件满足时开始。来电响铃、监控、离线演示和人脸检测均不启动上行录音。
9. 离线样本始终明确标注“演示”；正式接待失败时不能自动切换为演示，离线模式不请求录音或发送真实控制命令。

## 6. 启动、配置与可用性场景

首页提供四类主状态：“等待来电”“正在恢复接待”“接待受限”“暂不能接待”；主动停用时单独显示“门禁接待已停用”。网络正常不覆盖通知、锁屏等能力缺失。现场验证结果记录在验收文档，不新增应用内验收管理功能；权限检查不能替代实际验收。

| 编号 | 场景 | 用户看到的内容与按钮 | 系统处理与恢复 |
| --- | --- | --- | --- |
| A01 | 首次安装、尚未启用 | “启用门禁接待”；显示必须补齐的本户配置 | 从可见页面启动；检查配置后监听。麦克风和相机能力分开设置 |
| A02 | 本户或单元门机编号缺失/无效 | “请填写本户和单元门机编号”；“去配置” | 不启动真实接待；保存有效配置后自动重新检查 |
| A03 | 地库参数未配置 | 对应入口说明“尚未配置”；“配置此门机” | 仅限制该路监控，单元门和其他已配置入口保持可用 |
| A04 | 已启用，网口正常、监听正常 | “等待来电”；设置中可见最近门机回应时间 | 静默等待合法来电，不持续发监控请求维持“在线” |
| A05 | 前台服务启动被系统拒绝 | “后台接待未启动”；“启用接待”或“检查系统设置” | 保留前台可操作界面；从用户可见操作重试，后台不反复启动 |
| A06 | 通知权限关闭 | “接待受限：来电通知未开启”；“开启通知” | 前台来电仍显示；不宣称后台/锁屏提醒可靠。返回后重新检查 |
| A07 | 全屏来电授权缺失（适用系统） | “接待受限：锁屏来电展示未开启”；“检查锁屏来电” | 使用允许的通知降级，不绕过系统后台界面限制 |
| A08 | 系统后台管理限制尚未配置 | “后台接待稳定性待验证”；“查看设置指引” | 不把省电白名单状态当作整机验收；现场验证后记录结果 |
| A09 | 用户在 App 内停用接待 | “门禁接待已停用”；“重新启用” | 立即结束资源并保存停用意图；保存失败说明“停用设置未保存，重启前请重试”。成功保存后开机和网络恢复不能擅自重新启用 |
| A10 | 配置读取/迁移失败 | “无法读取门禁配置”；“检查配置”“查看详情” | 保留原数据；不回写空值、不进入演示、不自动沿用不完整身份 |
| A11 | 从系统设置返回，权限发生变化 | 当前能力即时更新 | 恢复当前状态快照；没有新用户动作不发送接听/开锁 |

## 7. 网络与恢复场景

网络就绪条件是有效以太网 Network、有效本机 IPv4/前缀、与手动配置相符、所需端口打开；不要求互联网验证通过。每个 UDP Socket 继续绑定对应以太网 Network，Wi-Fi 变化不能把门禁流量转走。

| 编号 | 场景 | 提示与操作 | 系统处理与恢复 |
| --- | --- | --- | --- |
| N01 | 网线未插或网卡不存在 | “未连接对讲网，请检查网线和网卡”；“查看连接详情” | 等待网口事件，不持续空转重开 Socket |
| N02 | 有网卡但尚无有效地址 | “正在等待有线地址”；10 秒后补充“仍未取得地址，请检查系统网口设置” | 继续监听地址变化；地址就绪立即尝试连接 |
| N03 | 实际地址与本户配置不符 | “有线地址与配置不符”；详情并列实际值与期望值；“检查配置” | 等待配置或网口变化，不无限重试错误配置，不代改系统地址 |
| N04 | UDP 端口打开失败或已被占用 | “接待连接暂不可用，正在重试”；“立即重试”“查看详情” | 按规定退避重开；详情给出可核对的错误原因，不直接断言其他 App 占用 |
| N05 | 权限等确定性错误导致无法绑定 | “无法建立接待连接，请检查权限和配置”；“查看详情” | 停止定时重试；相关权限、配置或网口变化后重新判断 |
| N06 | 通话/监控期间断网 | 来电页“连接已中断”；监控页“对讲网已断开” | 立即停铃、停录音/播放、取消旧计时和媒体；清空旧会话后恢复监听 |
| N07 | 网线、网卡重新接入或地址改变 | “正在恢复接待”，随后“等待来电”或具体故障 | 使用新 Network/地址重建；同一时间只允许一个连接和重试任务 |
| N08 | 门机无回应，但本机监听正常 | “暂未收到该门机回应”；“重试”“检查此门机配置” | 保留本户来电监听；仅本次监控/呼梯超时，不全局报断网 |
| N09 | 原室内机/同户身份冲突，原因未确定 | “连接异常，需检查设备和本户配置”；详情提供时序与参数 | 不自动更换房号、MAC 或其他身份，不推断确定原因 |
| N10 | 长时间没有来电 | 保持“等待来电”，最近回应时间如实变旧 | 无来电不是故障，不能为此不断重启健康监听 |
| N11 | 连续网络抖动、旧失败回调晚到 | 显示当前一次恢复状态 | 去重网口事件；旧连接回调无效，不能关闭新 Socket |

I/O 和端口资源暂时失败使用确定的退避序列：0.5、1、2、5、10、30 秒，之后维持 30 秒。只有稳定监听 60 秒或收到合法本户/门机报文才重置失败次数；仅成功创建 Socket 不能立即清零。手动立即重试取消原任务并只发起一次，新有效网口/地址变化立即评估一次。

恢复时可以发送一次已有协议依据的设备发现请求，记录门机是否回应；未回应不等于本机不能监听。探活不使用监控开始、接听、开锁或呼梯命令。

## 8. 来电、操作和页面切换场景

| 编号 | 场景 | 提示与操作 | 系统处理与恢复 |
| --- | --- | --- | --- |
| C01 | 前台、后台或系统锁屏收到有效本户来电 | 前台显示来电页；后台/锁屏发系统来电通知并请求展示来电页 | 校验通过后才响铃/亮屏；同一通只建立一个来电展示 |
| C02 | 重复来电请求 | 保持当前状态，不重复弹页/响铃 | 继续必要协商，但不自动接听，不重置响铃总时限 |
| C03 | 门机在来电页出现前取消 | 撤销通知与待展示来电页 | 旧页面即使稍后打开也只能显示“来电已结束”，不能恢复铃声 |
| C04 | 接听按钮连点、通知与页面同时接听 | 按钮短暂显示处理中，状态以统一快照为准 | 当前通只发送一次接听；重复动作返回当前结果 |
| C05 | 响铃无人接听 | 最多响铃 60 秒；显示“未接来电”结束原因 | 结束当前来电并停资源；8 秒无有效数据保护继续独立生效 |
| C06 | 监控期间来电 | 切到来电页，保留原来选择的门机 | 结束主动监控；通话后回选择页，不自动重开监控 |
| C07 | 编辑配置期间来电 | 来电页优先；原字段草稿保留 | 结束后回原设置草稿；不自动保存或丢弃草稿 |
| C08 | 当前来电期间请求修改连接配置 | “通话结束后可修改连接参数” | 禁用会影响连接的保存动作；音量等局部设置可立即生效 |
| C09 | 系统 Home、锁屏、旋转或 Activity 重建 | 来电/通话状态保持 | 页面解绑不挂断；重新打开订阅同一来电。页面内挂断/返回仍表示主动结束 |
| C10 | 手动挂断/来电页返回 | 立即回到原页面或原系统锁屏 | 发送一次结束请求并停资源；旧按钮和计时器失效 |
| C11 | 对端结束、8 秒无数据或连接中断 | 来电页显示具体结束原因，操作立即禁用；3 秒后返回，可提前返回 | 先停止音频与流量，再展示原因。新来电可立即替换该结束页 |
| C12 | 旧通知、旧权限结果或上一通的按钮 | “该来电已结束”或静默关闭过期通知 | 标识不匹配时不发送控制命令，不影响下一通 |
| C13 | 其他住户、其他来源、坏包 | 不弹用户故障，不响铃/亮屏 | 严格过滤，诊断计数按频率汇总，避免日志刷屏 |
| C14 | 来电期间已有呼梯等待 | 来电页照常工作，呼梯结果仍在运行状态中保存 | 保留现有独立呼梯窗口，不重发、不因切页误判失败 |

锁屏来电页仅开放本次来电的视频、接听、挂断和开锁；连接参数/诊断详情跳转需经过正常解锁流程。有系统安全锁时不尝试绕过密码。没有安全锁时也使用同样的会话和命令校验。

## 9. 音视频和实际命令异常

| 编号 | 场景 | 用户交互 | 系统处理与恢复 |
| --- | --- | --- | --- |
| M01 | 来电暂未出画 | 初始“正在连接画面”；5 秒仍无完整帧时“暂未收到画面，可接听” | 控制仍有效时保留接听/开锁；不使用坏帧刷新画面健康时间 |
| M02 | 已有画面停止更新 | 3 秒没有新完整帧后覆盖“画面已暂停”，不得继续标为实时 | 保留有效通话；新完整帧恢复时清除标记 |
| M03 | 麦克风未授权/被系统禁用 | “当前只能收听，对方听不到你”；“开启麦克风” | 允许接听和单向收听；只有用户在可见页面恢复授权后才能恢复上行录音 |
| M04 | 麦克风初始化或录音失败 | “麦克风暂不可用，对方听不到你”；“重试语音” | 单独停上行录音，保留播放、视频和控制；不整通误报断网 |
| M05 | 扬声器/播放失败或音频焦点丢失 | “暂时无法收听”或“语音被其他声音占用”；“重试语音” | 播放与录音状态分别更新；焦点丢失时暂停相应音频，恢复不重新发送接听 |
| M06 | 铃声音量为零/系统静音 | 首页能力提醒“来电铃声已静音”；来电页保留视觉提示 | 尊重系统音量与勿扰设置，不擅自提音量或绕过勿扰 |
| M07 | 可识别的视频解码失败、积压 | 持续异常时“画面暂不可用”；控制按钮保留 | 无效帧不刷新健康状态，显示只保留最新完整帧；实测控制响应不足再分离解码，不重发接听 |
| O01 | 用户点开锁 | 显示“正在发送”；本次请求处理中禁用重复提交 | 命令进入执行前核对当前连接和来电，等待超过有效期则拒绝；每次有效点按最多发送一次 |
| O02 | 开锁本地发送完成 | “开锁请求已发送，请确认门锁” | 按当前开关决定是否在发送完成 3 秒后挂断；1.5 秒后才允许下一次有效点按 |
| O03 | 开锁发送结果未确认/发生异常 | “未能确认开锁请求结果，请查看门锁状态”；网络仍有效时保留挂断 | 不自动重发；处理结果未明确前禁用重复开锁。故障详情说明最后本地阶段 |
| O04 | 开锁处理超过 1 秒但尚未返回 | “开锁请求仍在处理，请勿重复操作” | 界面等待超时不能当作“未发送”；保留处理状态直到结果或连接/会话失效 |
| O05 | 没有有效来电、来电刚结束或旧命令排队 | “该来电已结束”，开锁不可用 | 命令执行前校验并拒绝；重连后不补发 |
| O06 | 呼梯发现/回应超时 | “未收到门机回应，请确认后重试”；“重试” | 保留现有 2 秒发现、3 秒回应窗口，重试由新用户点按发起 |
| O07 | 收到呼梯回应 | “门机已回应，请留意电梯到达” | 不显示“电梯已到”；不自动补发或持续呼梯 |
| O08 | 主动监控占线、出画超时、30 秒结束 | 分别显示“门机占线”“暂未收到画面”“本次查看已结束” | 占线/超时允许手动重试；正常 30 秒或门机结束返回选择页，独立呼梯不取消 |

本地未开始发送的过期命令可以明确拒绝；进入系统发送后出现异常只能报告未确认结果。一次新开锁由新的用户点按产生，不能把“自动重试”伪装成新操作。现有重复开锁重置 3 秒自动挂断的规则保留；关闭自动挂断后的新开锁取消旧自动挂断计时，已经结束的来电不能被设置变化复活。

## 10. 屏幕、人脸与无人待机

| 编号 | 场景 | 策略与交互 |
| --- | --- | --- |
| S01 | 正常触摸或按键 | 立即正常亮度，刷新操作时间 |
| S02 | 连续确认有人约 0.5～1 秒 | 第二期恢复正常亮度；具体确认窗口定为 800 毫秒 |
| S03 | 无人且 30 秒无操作，无来电/监控 | 进入应用内低亮待机；待机亮度初值 5%，正常亮度跟随系统 |
| S04 | 响铃、已接听或主动监控 | 保持正常亮度；无人检测不得挂断、开锁或结束有效监控 |
| S05 | 相机拒绝、被占用、检测失败 | “感知亮屏暂不可用，点击屏幕唤醒”；回到触摸与 30 秒空闲低亮策略。未知不当作无人结果 |
| S06 | 夜间空闲 | 默认 22:00～06:00；检测降频，来电仍按当前铃声设置接待，不自动静音 |
| S07 | 用户按电源真正锁屏 | 第一期开锁屏来电通道；人脸是否能从该状态唤醒需第二期单独验收 |
| S08 | 供电断开/低电量 | 明确“外部供电已断开”；先降低屏幕/检测负载，电量不高于 10% 暂停感知检测，门禁接待保持启用 |
| S09 | 新来电打断低亮/系统息屏 | 立即由来电展示流程处理，优先级高于人脸与待机计时 |

人脸检测仅使用本地随包模型，不上传帧；正常最多每 200 毫秒分析一次，稳定无人/夜间最多每 2 秒一次，不叠加跳帧算法造成不可预期延迟。恢复触摸后取消旧降亮任务；任何旧结果均不能覆盖当前来电的亮屏需求。连续检测错误不无限快速重绑相机，等待资源变化或用户“重试感知”再恢复。

应用内低亮和系统息屏是两个状态。第一期不依赖摄像头实现接待；第二期仅在真机通过摄像头持续可用、亮屏时延和功耗验收后，才开放“系统息屏后感知唤醒”。该能力未通过时保留应用内低亮模式，并如实显示可用范围。

## 12. 启动、电源与可观测性

启用意图与运行所需身份/地址、自动挂断开关由 `AppSettings` 统一存入 Direct Boot 可用的应用配置；界面与服务读取同一权威记录，保留现有字段和默认值。网关、原机 MAC、中心地址等不参与启动的注记保留在普通私有存储，不建立两套同义运行参数。第一次升级迁移成功前保留原记录，迁移后不自动从旧参数回退；保存失败不激活未保存值，读取异常显示配置故障。录音、视频和敏感凭据不放入启动配置。

锁定启动、正常启动和应用更新都进入同一个幂等恢复入口，多个事件不能建立多个连接。启动阶段只恢复监听，不启动麦克风或摄像头。

系统恢复进程后只恢复“启用接待”的意图，活动来电、监控、自动开锁挂断计时和用户命令全部重新建立。App 内停用与系统强行停止需要分别说明；普通应用不能保证被系统强行停止后自行恢复，也不能伪造中断期间的未接记录。

专用接待启用且监听就绪或存在活动来电时，CPU 保活与亮屏分离管理；设计为单实例、非引用计数、每次最多持有 10 分钟，每 60 秒核对条件并续期。停止接待、资源释放或无网口且无活动会话时释放。系统休眠/厂商策略仍可能限制执行，因此持续供电、电池管理设置和实际后台接待测试都是交付条件，不能以持有锁为通过依据。

现有设置页补充当前接待能力、实际网口参数、最近合法回应、重试进度、最近故障和恢复入口；界面直接使用当前状态，不做历史查询系统。详细排查继续使用现有 `Maichi` 日志，记录状态变化和有限错误摘要，不记录原始音视频/报文。相同持续故障不重复弹提示，异常报文计数最多每 60 秒汇总一次。没有系统退出原因时只说明“接待曾中断”，不自行断言系统杀进程。

独立诊断页、历史事件数据库、诊断导出和设备管理框架不属于本轮范围；今后遇到实际维护需求时再评估。

## 13. 开发与验收顺序

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 | 核对基线和部署前提，重构控制器与统一配置 | 记录真实系统/网口条件；现有行为保持，旧配置入口移除 |
| P1 | Service 承载接待，声音从页面迁出，界面只订阅状态 | 后台不再停止监听，资源只有一个所有者 |
| P2 | 独立锁屏来电页与故障交互，复用现有设置页 | 主页面旧来电分支删除，权限不足/局部失败可解释并恢复 |
| P3 | 在现有连接逻辑内完成重连、启动和电源恢复 | 旧回调不影响新连接，地址恢复问题有实测结论 |
| P4 | 全量回归及 24/72 小时现场验收 | 真实来电、声音、门锁和恢复通过后，才进入感知阶段 |
| P5 | 人脸检测与低亮待机 | 仅增加检测与屏幕规则，原接待逻辑不复制、不依赖检测结果 |

第一期验收矩阵至少覆盖：前台/后台/锁屏来电，有/无安全锁，未接/接听/挂断/开锁，对端提前结束，连续来电和旧通知，麦克风拒绝/播放失败，局部视频失败，通话中拔网线，拔插网卡，IP 变化，端口失败，重启后首次解锁前后，系统回收后恢复，用户停用/强行停止，静音与权限撤销。真机网络地址就绪后，恢复监听目标为 5 秒内；注入瞬时端口故障且地址未变时，按退避节奏恢复并记录耗时。收到完整合法来电信号后，前台/系统允许展示时，视觉与铃声启动目标为 2 秒内；计时起点不是门机尚未送达本机的数据。

测试工具分三层：纯状态/虚拟时钟单元测试，已有抓包回放与 Android 界面/生命周期测试，真实门机和平板现场测试。24/72 小时包含息屏、重复呼叫、网络抖动与插电条件观察；成功模拟报文不算实际门锁和双向声音验收。
